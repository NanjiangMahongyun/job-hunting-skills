# 技能包升级更新（体检 + 查漏补缺 + 优化）

## 这个 skill 干什么

对整套求职技能包做一次"体检 + 升级"，保证它始终贴合使用者的**当前处境**（求职阶段 / 求职方向 / 身份），而不只是一份静态文档。核心做四件事：

1. **审视意图**：技能包当前解决的到底是什么问题？是否还贴合使用者现在的处境？
2. **体检知识库**：政策 / 法律 / 数据是否过期？有没有没考虑到的新知识缺口？
3. **优化 skill**：各 skill 的提示词是否贴合意图？有没有步骤缺口？
4. **增加实用步骤**：补上使用者实际使用中暴露出的、没想到的步骤 / 新 skill。

**核心逻辑**：技能包是"使用者复盘驱动"的活系统，不是一次设计完。每次发现流程缺口、政策过期、方向变化，就通过本 skill 升级。

**参考依据**：

- 渠道存活与来源分级体检 → `knowledge-base/求职信息渠道与数据源清单.md`：第二步 A 时效性检查时必须重跑一遍"被当数据源的那些渠道还活着吗、链接还指向原页吗"，并复核其 ✅/⚠️/❌ 引用分级是否仍成立、各 skill 的数据源清单是否还在引用已失效入口（看准网 2024-09-30 关停就是这样被揪出来的）；第三步找"新渠道/新平台规则"缺口时以它为基线。
- 公开发布前的法律边界与免责写法 → `knowledge-base/公开发布与免责合规手册.md`：第六步附「发布前叠甲体检」的判定依据——名誉权与商誉（可核实事实 vs 侮辱性定性）、商业秘密与保密义务、他人个人信息、开源许可与署名、取证建议的合法边界、被投诉后的更正与下架流程。

## 什么时候用（触发时机）

| 触发场景            | 示例                               |
| --------------- | -------------------------------- |
| **定期**          | 每月 / 每季度一次例行体检                   |
| **求职阶段变化**      | 校招→社招、实习→转正、应届→在职跳槽              |
| **身份变化**        | 大学生身份 → 社会人员身份（进入 💼 社招分支）       |
| **方向调整**        | 换了目标岗位方向（如从 Java 后端 → AI Agent）  |
| **政策 / 市场重大变化** | 最低工资、社保基数、补贴政策调整；行业收缩 / 扩张       |
| **准备公开发布**    | 要把仓库 push 到 GitHub、分享给别人或发到社群——必须走「第六步附：发布前叠甲体检」，任一项未过就不发布 |
| **使用者复盘发现问题**   | "为什么没有 XX 分析？"这类反馈（技能包历次升级都由此驱动） |

## 执行流程（必须按顺序）

### 第0步：加载技能包全景

- 读 `README.md`、`README-使用索引.md`、`技能流程总览.html`；本地若另存着《技能使用与更新日志》（**不入库**）就一并读，用来对照上一轮的规范有没有退化
- 用 `ls .claude/skills/` 枚举 skill 清单（不要靠数字编号记忆），核对三份文件与磁盘是否一致
- **结构自检**：逐个确认 `SKILL.md` 首行是 `---`。分隔符被转义成 `\---` 会让 YAML frontmatter 失效，该 skill 装机后不被识别（目录迁移时曾踩此坑）
- 列出当前：知识库清单、skill 清单、版本号、适用对象
- **确认求职身份（🎓 大学生/应届 or 💼 社会人员）与求职阶段**——技能包的意图是否仍贴合使用者处境，取决于这个前提；身份变化（毕业/入职/离职）会让主线从 job-recommender 转向 job-switch-decision，需在升级报告开头写明
- 明确技能包当前**意图**（一句话）：帮求职者在信息不对称的求职博弈中不被压价、不被坑、高效决策。

**全量覆盖自检（用命令反查，不靠印象）**：一轮元更新往往同时改多个 skill 共有的前置步骤，最容易出的问题是"只改了其中几个"。逐条跑：

```bash
grep -rL "确认求职身份" .claude/skills/*/SKILL.md      # 输出应为空：每个 skill 都要有身份前置
grep -rn --include=SKILL.md '^[[:space:]]*[\\]---' .    # 输出应为空：首行被转义会让 frontmatter 失效（只在行首匹配，避免文档里引用该写法时自命中）
grep -rn "skill 0[0-9]" .                                 # 只允许命中本文件「禁止行为」那条规则自身；出现别的命中就是改名后遗留的悬空编号引用
for f in knowledge-base/*.md; do n=$(basename "$f" .md); printf "%-24s %s\n" "$n" "$(grep -rl "$n" .claude/skills/ | wc -l)"; done   # 每行第二个数字应 ≥2：为 0/1 说明这份知识没被 skill 消费
```

### 第一步：审视技能包意图

1. **先问用户**（不靠猜）：当前求职阶段 / 求职方向 / 求职身份（大学生 or 社会人员）是什么？
2. **对照判断**：技能包现有设计（校招 / 社招分支 / 方向示例）是否还贴合？有无错位？
   - 例：用户从"实习期大学生"变成"在职跳槽"，技能包如果没有身份分支就错位了 → 需加社招内容
3. **输出**：意图评估结论 —— "贴合，无需调整" 或 "需调整：XXX"

> 规则：意图调整（如技能包方向、适用人群）**必须用户确认**，不擅自改。

---

### 第二步：知识库体检（清单核对）

对**每一份**知识库做三类检查：

#### A. 时效性（重点，必须联网核实）

以下数据类内容逐项用当前时间联网复核，过期就更新：

| 核对项         | 说明                  |
| ----------- | ------------------- |
| 最低工资        | 当地现行标准（逐年调整）        |
| 社保缴费基数上下限   | 逐年调整                |
| 公积金比例       | 5%-12%，看是否有变动       |
| 人才补贴 / 落户政策 | 应届生补贴、生活/租房补贴、落户办法  |
| 应届生认定标准     | 各地放宽趋势，逐年变化         |
| 法律新规        | 劳动合同法 / 就业促进法相关修订   |
| 目标行业薪资数据    | 目标行业 / 岗位的应届 / 社招行情 |

> 发现数字与当前不符 → 更新并标注来源 URL；搜不到新数据 → 标注"待核实，以官方最新为准"。

#### B. 完整性

技能包知识库是否覆盖求职生命周期的每个环节？

| 生命周期阶段             | 是否覆盖 | 对应知识库         |
| ------------------ | ---- | ------------- |
| 求职前（简历/方向/身份）      | ？    | AI辅助求职实操教程、求职心理指南、校招与社招时间线全景 |
| 投递中（渠道/岗位/反诈）      | ？    | 求职信息渠道与数据源清单、毕业常识（投递/反诈部分） |
| 面试（尽调/谈薪/合同）       | ？    | 面试高频问题与作答框架、公司类型画像与选择指南、自身优势与公司劣势通用框架、社招谈判指南  |
| offer 与入职（社保/公积金/个税） | ？    | 五险一金与个税实操手册、毕业常识 |
| 在职/离职（社保/竞业/补偿/背调） | ？    | 离职与背调合规手册、五险一金与个税实操手册、毕业常识  |
| 行业（目标行业动态）         | ？    | 行业背景分析（产出报告）  |
| 沟通与协作边界（职场行为）     | ？    | 职场小技巧与人情世故（只到"减少误会、保护自己、可追溯"为止，见其立场说明） |

缺环节 → 记为缺口。

#### C. 缺口（没想到的新知识）

对照求职场景主动发散，找"可能没想到"的知识：

- 新政策 / 新补贴（如一次性扩岗补助扩范围）
- 新骗局 / 新反诈场景（如 AI 面试骗局、培训贷变种）
- 新渠道 / 新平台规则
- 新身份场景（社招 / 考公考编 / 灵活就业 / 创业）
- 新行业方向（如 AI 应用工程、出海）

---

### 第三步：查漏补缺（更新 or 新增）

针对第二步发现的缺口，二选一：

- **更新现有文件**：数字过期、内容过时 → 就地修订，保留原文结构与标注方式
- **新增知识库文件**：存在独立的新知识域 → 新建，遵循既有命名与格式，并标注：
  - 定位（解决什么）
  - 适用人群（大学生 / 社会人员 / 通用）
  - 与哪个 skill 配合
- 新增后同步 README（知识库清单）
- **新增文档必须接线**：写进 knowledge-base 不等于被使用。每份新文档至少要出现在一个 skill 的「参考依据」列表和「协作链路」里，并说明"这个 skill 的哪一步用它"。反查方法：

```bash
for f in knowledge-base/*.md; do n=$(basename "$f" .md); printf "%s: %s\n" "$n" "$(grep -rl "$n" .claude/skills/ | wc -l)"; done
```

  引用数为 0 的文档＝知识孤岛，要么接线要么删掉（一次性新增多份时，靠这条发现"面试/时间线"两份最初只被 1 个 skill 用到）。
- **数字口径一致性**：同一政策数字（社保基数、最低工资、一裁终局上限）在 skill 与 knowledge-base 里各写一遍时，以 knowledge-base 为准逐处核对；未核实的显式标注「未查到」，不保留看起来精确的旧数字。

---

### 第四步：优化 skill 提示词

对每个 skill 检查四个维度：

1. **意图贴合**：该 skill 的"输入→处理→输出"是否服务技能包整体意图？有无偏离？
2. **步骤缺口**：有没有"分析完该做下一步却没做"的情况？
   - 历史案例：分析完简历没做行业分析、尽调前没定目标公司——都是后来补上前置步骤才走顺的
3. **提示词清晰度**：触发词、执行顺序、禁止行为、输出格式是否明确可执行？
4. **跨 skill 衔接**：与其他 skill 的协作链路是否完整？（如 job-negotiation-strategist 联动 job-recommender / company-due-diligence / industry-background-analyzer）

有缺口 → 就地修订该 skill；修订后同步 README 对应 skill 描述。

---

### 第五步：增加实用步骤 / 新 skill

1. **找步骤缺口**：回顾使用者最近几次真实使用，有没有"做完一步不知道该干嘛""卡住没工具"的情况
2. **判断是否新增 skill**（需同时满足）：
   - 方法论足够独立（不是某 skill 的一个步骤）
   - 场景足够高频（不是一次性）
   - 有清晰的输入→输出
3. **新增 skill** 遵循既有规范：YAML 头（name/description/触发词）+ 结构化执行流程 + 输出格式 + 禁止行为
4. 新增后同步 README（目录树 + skill 清单）

---

### 第六步：同步 README + 索引 + 流程图

升级后必须同步对外文档（技能包一致性约定）：

| 文件                    | 更新内容                           |
| --------------------- | ------------------------------ |
| README.md             | 入口表、目录树、免责要点；**不写"第几版改了什么"**   |
| README-使用索引.md       | 适用对象 / 知识库清单 / skill 清单 / 描述   |
| 技能流程总览.html          | 新增节点 / 分支、底部注释；badge 只随基线标识变动 |
| 本 skill「维护规范」表       | 新约束补进这张表——它是本包规范的**唯一权威**；逐轮修订只进 git 提交信息，**不逐轮新开版本号** |

> 版本标识是给接手维护的人看的坐标，不是施工日志。对外文档（README / 索引 / 流程图 / 知识库 / SKILL.md）里不出现"某版新增／某版修复"这类演进叙述——那属于维护者本地的对账记录（不入库）。

---

### 第六步附：发布前叠甲体检（要把仓库 push / 公开 / 交给别人时必做）

**触发**：任何"上传、分享、fork 给别人、发到社群"的动作。这一步与内容升级无关，只回答一个问题——**这份东西公开出去，会不会让我陷入纠纷、被追责、或被人当成教唆**。

判断标准只有两条：**内容确实符合你在显眼处做出的承诺**；**任何一处指控或结论都能落到可核实的事实上**。叠甲不是删掉有用内容，是把"不针对真实主体、不教造假、不构成法律意见、有更正渠道"写明，并且让内容真的配得上这四句话。

| 检查项 | 怎么查 | 不过怎么办 |
|---|---|---|
| ① 隐私：本地路径、账号、手机号/身份证样式、邮箱、真实人名 | `grep -rEn -e 'Users[\\/][A-Za-z0-9_.-]+' -e '1[3-9][0-9]{9}' -e '[0-9]{17}[0-9Xx]' --include=*.md --include=*.html .` | ⚠️ URL 里的长数字串会假阳性，命中后逐条看上下文；确认是真实信息的一律改写为虚构示例，而不是打码 |
| ② 个人记忆库与生产文件落点 | `git ls-files \| grep -iE -e '^memory/' -e 'profile\.md' -e 'current-state\.md' -e 'career-timeline\.md' -e 'analysis-archive'` 应为空；`.gitignore` 里必须有 `/memory/`。再看**落点有没有越界**：`find . -maxdepth 1 -type f -name '*.md' -not -name 'README*' -not -name '技能*' -print` 必须为空——岗位池、尽调报告、简历这类生产文件只允许待在 `memory/` 下（见 memory-manager「生产文件落点总表」），出现在仓库根就等于把真实公司名写进了公开库 | 先从索引移除，再确认工作树与历史都没有残留；落点越界的文件移到 `memory/` 对应目录 |
| ③ 历史提交（不止当前工作树干净，**也不止文件内容**） | `git log --all --diff-filter=A --name-only --pretty=format:` 逐条看是否曾提交过隐私文件；再 `git config --get-regexp user\.` 与 `git log --all --pretty=format:'%an <%ae>'` 看每条提交携带的**作者名与邮箱**——它不在任何文件里，所有针对文件内容的 grep 都查不到它，但 push 之后永久公开且可被爬 | 历史含隐私不能靠后续提交掩盖，需重建历史（属破坏性操作，先与使用者确认）；作者身份未 push 时最省事——给本仓库单独设 `git config user.name/user.email`（不加 `--global`）后重做提交，或直接删 `.git` 重新 `init` |
| ④ 是否指向真实主体 | `grep -rn --include=*.md -e 黑厂 -e 无良 -e 名声很差 -e 口碑最差 .`；命中必须出现在"不这样下结论"的规则句里；再用 `grep -rn "腾讯\|阿里\|字节\|华为" --include=*.md .` 确认每处只是渠道举例或来源引用，不是对某公司的负面结论 | 改成 XX 公司 + 结构性描述；公司点评只写"可核实事实 + 基于事实的风险推演"，见 company-due-diligence「最高优先级铁律」第 5 条 |
| ⑤ 造假/规避类措辞是否在禁止语境 | `grep -rn --include=*.md -e 伪造 -e 虚报 -e 虚构 -e 隐瞒 -e 规避 -e 钻空子 .` 逐条确认上下文有 🚨／❌／红线标记 | 改写为"真实前提下的表述方式 vs 造假"对照表；保留自我保护内容，删掉只有隐瞒真相才有效的建议 |
| ⑥ 取证建议与法律表述是否越界 | 取证类：跑 `grep -rn --include=*.md -e 录音 -e 全程录音 -e 截图留证 .`，逐处确认**同一段**写了边界（只录本人参与的对话；不窃听他人、不诱导陈述、不剪辑、不伪造销毁证据）——只在别处写边界、正文单喊"全程录音"＝没过。定性类：跑 `grep -rn --include=*.md -e 涉嫌 -e 构成侵权 -e 违法 -e 司法实践 .`，确认没有替读者对某类主体下结论，也没有把某地裁判尺度写成全国保证。依据类：确认引用的司法解释仍属现行（例：原《合同法解释（二）》已于 2021-01-01 废止，其"30%"要改引《民法典》合同编通则解释第 65 条），条号写法用"第五百八十五条"而非"第 585 条"时也要能对上 | 见《公开发布与免责合规手册》第二、六节。把边界写进原文而不是留给读者自觉；结论改为"可能／以受理机关认定为准"；失实或已废止的依据换成现行文本并补核实日期 |
| ⑦ 免责与立场声明 | 确认 README「这个仓库的立场」与各文档尾部免责声明都在，且声明内容与实际文本一致（例如声明"示例均为虚构"时，全文确实无真实主体）；跑 `grep -rL "不构成法律意见" knowledge-base/*.md`（应为空）与 `grep -rL "开 issue"`（检查更正渠道） | 补齐声明；**声明与内容矛盾比没有声明更糟** |
| ⑧ 开源许可与署名 | 确认借鉴来源给出仓库 URL 且逐条实测可访问；确认根目录有 `LICENSE`（技术类仓库建议 MIT 或 Apache-2.0，后者含专利授权条款）；确认没有把他人仓库改名当自己作品 | 补 LICENSE 与署名；核不到的链接改为官网检索指引，不放推测出来的 URL |
| ⑨ 可用性（别人 clone 下来能不能用） | 每个 SKILL.md 首行是裸 `---`、`name` 与目录名一致；文件内只用相对路径；`grep -rn "knowledge-base/" .claude/skills/` 引用的文档都存在；**协作链路里引用的 skill 名必须真实存在**（命令见下面「引用完整性」块）；每个产出 skill 都要有「完成后 → memory-manager 归档」那一行；确认 GitHub 首页会渲染什么——**必须有根 `README.md`**（GitHub 只渲染这个名字，`README-使用索引.md` 不会被渲染），且它是薄首页、与详版索引互链、两页定位不重叠；**表格里没有未转义的竖线**（GitHub 会把那一行切成多列，访客看到的就是错位内容；awk 列数比对见下面「引用完整性」块第 5 条） | 补结构/路径/README；把不存在的 skill 名换成本包真实 skill 或改成指向 `knowledge-base/` 文档；补断掉的归档接线；串列的表格把单元格里的 grep 改成 `-e 词1 -e 词2` 多模式或补上转义；命名一律 kebab-case，仓库名不含中文 |
| ⑩ 时效与链接 | 抽查来源链接是否仍指向原页；已关停渠道（如看准网 2024-09-30）不得再作为数据入口出现 | 逐处替换为仍服务的入口，并标注核实日期 |

**引用完整性与落点接线（②⑨ 用的五条命令，仓库根目录执行，2026-10-22 实测可用）**

```bash
# 1) 协作链路里引用的 skill 名，是否都对应真实目录？输出里凡是长得像 skill 名
#    （-generator / -analyzer / -prep / -optimizer / -comparison / -tailor）却不在下面 12 个目录里的，就是悬空引用
ls .claude/skills | sort > /tmp/skills.txt
grep -rhoE "\b[a-z]+(-[a-z]+)+\b" .claude/skills/*/SKILL.md | sort -u > /tmp/cited.txt
comm -13 /tmp/skills.txt /tmp/cited.txt | grep -E "generator|analyzer|prep|optimizer|comparison|tailor$"   # 应为空

# 2) 已废弃的数字编号引用（NN-中文名）是否还残留？（此写法会跳过 2026-10-21-公司尽调 这类日期文件名）
grep -rnE "(^|[[:space:]]|[│├└])[0-9]{2}-(岗位推荐|公司尽调|谈判筹码|谈薪执行|合同审核|补偿金|行业背景分析|JD分析)" .claude/skills/*/SKILL.md   # 应为空

# 3) 归档接线是否双向：产出 skill 各自有没有写「完成后 → memory-manager 归档/落盘」
grep -rlE "memory/(analysis-archive|job-pool|resume-)" .claude/skills/*/SKILL.md | wc -l   # 应为 11（除 skill-upgrade-maintainer 外的全部）

# 4) 生产文件有没有越界到要公开的地方（仓库根）
find . -maxdepth 1 -type f -name '*.md' -not -name 'README*' -not -name '技能*' -print   # 应为空

# 5) Markdown 表格有没有"串列"：单元格里写了未转义的竖线，GitHub 渲染时会把这一行切成多列
#    （拿每行的竖线数与表头比对；输出应为空。写法要求：单元格里的 grep 用 -e 多模式，竖线必须转义成反斜杠+竖线）
awk '!/^[[:space:]]*[|]/ { intable=0 }
     /^[[:space:]]*[|]/  { BS=sprintf("%c",92); l=$0; c=0
       for (i=1; i<=length(l); i++) if (substr(l,i,1)=="|" && substr(l,i-1,1)!=BS) c++
       if (!intable) { ref=c; intable=1 }
       else if (c!=ref) printf "%s:%d 竖线=%d 应=%d  %s\n", FILENAME, FNR, c, ref, substr($0,1,40) }' \
     $(find . -name '*.md' -not -path './.git/*' -not -path './memory/*')   # 应为空
```

**复用提示（踩过的坑写成可判定规则）**

- **通用前置要全量覆盖**：影响"后续查什么、怎么定价"的前置步骤必须写进每个 SKILL.md，并用 `grep -L` 反查谁没写——只改"核心几个"必然留下分支缺口。
- **渠道与链接会过期**：每轮元更新重跑一遍"被当作数据源的入口是否还活着"；建渠道清单时顺带扫全库旧引用，能一次揪出多处过期入口。
- **新增知识要接线**：写进 `knowledge-base/` 不等于会被使用，靠引用计数确认它接进了某个 skill 的某一步。
- **价值观边界写成规则**：删掉自我保护的内容不是修法（留痕、拒绝、边界都正当）；给每条做法加可判定的界线才是——真实陈述与造假的界线必须写在同一张表里。
- **自查命令要能重跑**：凡是靠"我检查过了"成立的结论，下一轮都要能同一条命令再跑一遍。写不进命令的检查（比如"内容看起来很安全"）等于没有检查。
- **命令写进表格前先想渲染**：Markdown 表格的单元格里出现裸竖线，GitHub 会把这一行切成多列——叠甲体检表自己的四条 grep 就这样坏过。规则：单元格里的匹配用 `-e 词1 -e 词2` 多模式，不用竖线管道；并用上面第 5 条 awk 命令复查。

## 禁止行为

1. ❌ 不因"看起来全面"而堆内容——缺口必须实际存在才补，不制造伪缺口
2. ❌ 不编造政策 / 法律 / 数据——时效性内容必须联网核实并标来源，搜不到写"待核实"
3. ❌ 不擅自改变技能包核心方向 / 适用人群——意图调整需用户确认
4. ❌ 升级后不同步 README / 索引 / 流程图——对外文档必须一起更新，否则版本标识不一致；反过来也不要每轮小修都新开版本号，日常修订进 git 提交信息
5. ❌ 不动用个人记忆库（memory/）内容做"通用知识"——那属于隐私，不进入方法论
6. ❌ 不用数字编号（skill 00/02…）引用 skill——一律以 `.claude/skills/<name>/SKILL.md` 为准；凡改名或拆分，必须全库扫一遍悬空引用（`grep -rn "skill 0[0-9]\|skills/0[0-9]"`）并同步 README 与流程图
7. ❌ 不跳过「发布前叠甲体检」就 push / 公开 / 交给别人——内容本地可用不等于公开无风险；任何一项未过就不发布
8. ❌ 不写兑现不了的声明——"示例均为虚构""不针对真实主体""不构成法律意见"这类声明必须与全文实际内容一致；**声明与内容矛盾，比没有声明更糟**
9. ❌ 不把"自我保护"删成"什么都不说"——留痕、拒绝、边界、依法取证都正当；要划掉的是以隐瞒或伪造为前提的建议，判据是"当着对方的面说出来你是否还愿意承认"
